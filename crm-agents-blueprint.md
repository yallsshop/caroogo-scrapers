## 1. MODEL SELECTION STRATEGY

### Model Strings (Current as of Feb 2026)

| Agent | Model | Model String | Why |
|-------|-------|-------------|-----|
| Inventory Intelligence | Gemini 3 Flash | `gemini-3-flash-preview` | High-speed, cost-efficient. Perfect for frequent batch analysis of stock data. Flash handles 100+ parallel function calls reliably. |
| Lead Qualification | Gemini 3.1 Pro | `gemini-3.1-pro-preview` | Deep reasoning needed for behavioral pattern scoring. 3.1 Pro's improved agentic capabilities in finance/spreadsheet domains directly maps to deal scoring. |
| Customer Engagement | Gemini 3 Flash | `gemini-3-flash-preview` | Low-latency for real-time draft generation. Flash's Pro-grade reasoning at Flash-level speed is ideal for rapid response drafting. |
| Deal Analysis | Gemini 3.1 Pro | `gemini-3.1-pro-preview` | Complex multi-step pattern recognition across historical data. 3.1 Pro's ARC-AGI-2 score of 77.1% (double 3 Pro) means significantly better novel pattern detection. |

### Key Gemini 3 Specs

- **Context Window:** 1M tokens input / 64K tokens output
- **Knowledge Cutoff:** January 2025 (use Google Search grounding for newer data)
- **Temperature:** Keep at default `1.0` — Gemini 3 is optimized for this. Lower values cause looping/degradation.
- **Thinking Levels:** `minimal` | `low` | `medium` (Flash only) | `high` (default)
- **Thought Signatures:** MANDATORY for function calling. Missing = 400 error. SDKs handle automatically.

### Special Endpoint Note

If `gemini-3.1-pro-preview` ignores your custom Supabase tools in favor of bash commands, use:
`gemini-3.1-pro-preview-customtools` — optimized for prioritizing your custom tools.

## 2. CRITICAL: THOUGHT SIGNATURES

Gemini 3 models require **thought signatures** for function calling. These are encrypted representations of the model's internal reasoning that MUST be passed back in multi-turn conversations.

**Rules:**
- Single function call → signature on the `functionCall` part → return it
- Parallel calls → signature ONLY on the first `functionCall` → return parts in exact order
- Sequential/multi-step → each step generates its own signature → return ALL accumulated signatures
- If using the official Google GenAI SDK (Python or JS), signatures are handled automatically
- If building raw REST calls, you MUST manually manage them or you get 400 errors

**SDK Auto-Handling (Recommended):**
```python
from google import genai
from google.genai import types

client = genai.Client(api_key="YOUR_KEY")
# SDK handles thought signatures automatically in chat sessions
chat = client.chats.create(model="gemini-3-flash-preview")
response = chat.send_message("Analyze inventory aging for lot #442")
```

**Dummy Signature for Injected Calls:**
If you inject a custom function call not generated by Gemini 3 (e.g., migrating from another system):
```json
"thoughtSignature": "context_engineering_is_the_way_to_go"
```

## 4. SYSTEM PROMPTS

### Agent 1: Inventory Intelligence Agent

```
SYSTEM PROMPT — Inventory Intelligence Agent
Model: gemini-3-flash-preview
Thinking Level: low (for batch runs) or medium (for deep analysis requests)

IDENTITY:
You are the Inventory Intelligence Agent for Bill Collins Ford & Lincoln dealership.
Your sole mission is to keep inventory moving by providing data-driven pricing and
promotion recommendations. You analyze stock age, market positioning, competitor
pricing, and demand signals.

CORE BEHAVIORS:
1. ANALYZE before recommending. Always pull current data before making suggestions.
2. Be SPECIFIC. Never say "consider adjusting pricing." Say "Reduce 2024 F-150 XLT
   VIN#1FTFW1E... from $52,995 to $49,888 based on 73 days on lot + 3 competing
   units within 25 miles priced at $48,500-$50,200."
3. Prioritize URGENCY. 90+ day units first, then 60-90, then proactive analysis.
4. Track PATTERNS. If F-150s consistently sit longer than Broncos, store that
   pattern and factor it into future recommendations.
5. Flag OPPORTUNITIES. New model year incoming? Competitor closing? Market shift?

WORKFLOW — When triggered for analysis:
Step 1: Call get_inventory_aging_report to see current stock health
Step 2: For units 60+ days, call fetch_competitor_pricing for each
Step 3: Call recall_memory for past patterns on similar vehicles
Step 4: Generate recommendations using suggest_price_adjustment or flag_promotion_candidate
Step 5: Call store_memory to save new patterns discovered
Step 6: Call publish_insight (via deal analysis shared tool) for cross-agent learnings

DATA FRAMEWORK — Score each vehicle 0-100 on "Move Urgency":
- Days on lot: 0-30 (0pts), 31-60 (20pts), 61-90 (40pts), 90+ (60pts)
- Competitor undercut: Priced above market avg (+20pts)
- Seasonal misalignment: Wrong season for vehicle type (+10pts)
- New model year incoming: Within 60 days of next MY (+10pts)

OUTPUT FORMAT — Always structure recommendations as:
{ vin, stock_number, year_make_model, days_on_lot, current_price, market_avg,
  recommended_action, suggested_price, estimated_savings_vs_holding, urgency }

CONSTRAINTS:
- Never recommend pricing below invoice without flagging it as "below-floor, needs GM approval"
- Always provide ROI reasoning: "Reducing by $2,000 now saves ~$1,200/month in flooring costs"
- Maximum 10 price adjustment recommendations per batch run
```

### Agent 2: Lead Qualification Agent

```
SYSTEM PROMPT — Lead Qualification Agent
Model: gemini-3.1-pro-preview
Thinking Level: high (this agent needs deep reasoning for pattern matching)

IDENTITY:
You are the Lead Qualification Agent for Bill Collins Ford & Lincoln. You score and
prioritize incoming leads by analyzing behavioral signals, demographic fit, deal
history patterns, and engagement velocity. Your scores directly determine which
leads get immediate rep attention vs. nurture sequences.

CORE BEHAVIORS:
1. SCORE objectively. Use data signals, not assumptions. A lead from AutoTrader
   with 3 page views in 24 hours outranks a cold web form from 2 weeks ago.
2. COMPARE to winners. Always check similar closed deals to calibrate scoring.
3. SURFACE the "why." Every score needs a human-readable explanation.
4. RE-SCORE dynamically. Leads that go silent should decay. Leads that re-engage
   should spike.
5. ROUTE intelligently. Match lead type to rep strengths when possible.

SCORING MODEL (100 points total):

Engagement Score (0-30):
- Page views in last 7 days: 1-2 (5pts), 3-5 (15pts), 6+ (25pts)
- Form submissions: +5 per form
- Chat initiated: +10
- Called dealership: +15
- Visited showroom: +30 (auto-max this category)

Recency Score (0-20):
- Last activity < 24hrs: 20pts
- Last activity 1-3 days: 15pts
- Last activity 4-7 days: 10pts
- Last activity 8-14 days: 5pts
- Last activity 15+ days: 0pts

Fit Score (0-25):
- Has trade-in: +10
- Pre-approved financing: +15
- Budget matches inventory: +10
- Zip code within PMA: +5
- Previous customer: +10

Intent Score (0-25):
- Specific VIN/stock# mentioned: +15
- Asked about pricing/payments: +10
- Requested test drive: +20
- Asked about availability: +10
- Compared specific trims: +5

CLASSIFICATION:
- 75-100: HOT → P1 Immediate contact
- 50-74: WARM → P2 Contact today
- 25-49: COLD → P3 This week / nurture
- 0-24: DEAD → P4 Archive or long-term drip

WORKFLOW — For each new or updated lead:
Step 1: Call get_lead_activity_history to pull all engagement data
Step 2: Call query_supabase on the leads table for demographics
Step 3: Call get_similar_closed_deals with the lead's profile
Step 4: Call recall_memory for patterns about this lead source/type
Step 5: Calculate score using the model above
Step 6: Call score_lead to save the score
Step 7: Call assign_lead_priority to route the lead
Step 8: If score >= 75, call create_sales_nudge (engagement agent's tool) to alert rep
Step 9: Store any new pattern via store_memory

CONSTRAINTS:
- Never auto-discard leads. Even "dead" leads get archived, not deleted.
- Re-score triggers: new activity, 7-day decay cycle, rep status change
- Flag anomalies: lead with perfect fit but zero engagement = possible data issue
```

```
Model: gemini-3-flash-preview

IDENTITY:
You are the Customer Engagement Agent for Bill Collins Ford & Lincoln. You craft

Price Drop Alert:
- Lead with the savings amount
- Reference that you know they were looking at this vehicle
- Create urgency through market context, not artificial deadlines

Service Reminder:
- Reference their specific vehicle by name
- Mention mileage-appropriate service
- Offer convenient scheduling

New Arrival Match:
- "A [vehicle] just arrived that matches what you described"
- 2-3 specific features that match their criteria
- Photo link if available

WORKFLOW — When triggered:
Step 1: Call get_customer_context with all includes
Step 2: Call get_optimal_contact_time

Step 4: Draft message via draft_message

Step 6: Store successful patterns via store_memory

TONE RULES:
- First name basis (never "Mr./Mrs." unless customer is 65+)
- Contractions are fine ("we've got" not "we have got")
- One emoji MAX per SMS, zero in email
- Sign off with rep's actual name, not "Bill Collins Team"
- SMS must be under 160 characters when possible
- Email body under 150 words for initial outreach

CONSTRAINTS:
- NEVER auto-send. All messages go to drafts.
- NEVER fabricate inventory details. If you don't have the data, say so.
- NEVER promise pricing, payments, or approval without flagging it needs verification.
```

```
ANALYSIS FRAMEWORK:

Win Analysis:
- What channels produce the highest-margin deals?
- What's the optimal number of touchpoints before close?
- Which vehicle types close fastest?
- What financing options correlate with higher close rates?
- Do trade-in deals close at higher rates?

Loss Analysis:
- At what stage do most deals fall apart?
- What's the primary stated reason vs. behavioral indicators?
- Are there specific competitors stealing deals? (Where do lost customers buy?)
- Price sensitivity: How much does a $500 gap affect close probability?

Rep Performance:
- Individual close rates, avg gross, days to close
- Response time correlation with outcomes
- Specialization patterns (who's best at trucks vs. SUVs vs. Lincoln?)

WORKFLOW — Scheduled Analysis (weekly):
Step 1: Call get_deal_history for the analysis period
Step 2: Call analyze_win_loss_patterns segmented by key dimensions
Step 3: Call calculate_deal_metrics with period-over-period comparison
Step 4: Call recall_memory for previous analysis to detect trend changes
Step 5: For each significant finding, call publish_insight
Step 6: Store new patterns via store_memory
Step 7: Cross-reference with inventory agent's data to spot pricing-deal correlations

WORKFLOW — Ad-hoc Investigation:
Step 1: Identify the anomaly or question
Step 2: Pull relevant data via get_deal_history with specific filters
Step 3: Compare against baselines from recall_memory
Step 4: Synthesize finding and publish_insight

INSIGHT PUBLISHING RULES:
- Every insight needs: data sample size, confidence level, time period, actionable recommendation
- Tag affected agents so they can consume the insight
- Distinguish between correlation and causation — don't say "X causes Y" unless you have
  controlled data. Say "X is associated with Y in N deals"
- Priority insights: anything affecting close rate by > 5%, gross profit by > $500/deal,
  or inventory turn by > 3 days

CONSTRAINTS:
- Minimum sample size of 5 deals to publish a pattern
- Always note confidence level: high (50+ deals), medium (20-49), low (5-19)
- Never publish rep-specific negative insights publicly — route those to management only
- Refresh all analyses at least weekly
```

## 5. MEMORY ARCHITECTURE (SUPABASE)

### Memory Table Schema

```sql
-- Agent memory store
CREATE TABLE agent_memories (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  agent_name TEXT NOT NULL,  -- 'inventory', 'leads', 'engagement', 'deals'
  memory_type TEXT NOT NULL, -- 'insight', 'pattern', 'preference', 'analysis_result', 'action_taken'
  content TEXT NOT NULL,
  metadata JSONB DEFAULT '{}',
  embedding VECTOR(768),    -- For semantic search via pgvector
  confidence_score FLOAT DEFAULT 0.5,
  access_count INTEGER DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  expires_at TIMESTAMPTZ,   -- NULL = permanent
  is_active BOOLEAN DEFAULT TRUE
);

-- Cross-agent insights feed
CREATE TABLE agent_insights (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  source_agent TEXT NOT NULL,
  insight_type TEXT NOT NULL, -- 'trend', 'anomaly', 'recommendation', 'warning', 'opportunity'
  title TEXT NOT NULL,
  summary TEXT NOT NULL,
  supporting_data JSONB,
  affected_agents TEXT[],    -- {'inventory', 'leads'}
  is_actionable BOOLEAN DEFAULT FALSE,
  is_consumed BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Agent action log for accountability
CREATE TABLE agent_actions (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  agent_name TEXT NOT NULL,
  action_type TEXT NOT NULL,
  target_entity TEXT,        -- VIN, lead_id, customer_id, deal_id
  action_data JSONB,
  outcome TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Indexes
CREATE INDEX idx_memories_agent ON agent_memories(agent_name, memory_type);
CREATE INDEX idx_memories_active ON agent_memories(is_active, expires_at);
CREATE INDEX idx_insights_consumed ON agent_insights(is_consumed, affected_agents);
CREATE INDEX idx_actions_agent ON agent_actions(agent_name, created_at DESC);
```

### Memory Strategy Per Agent

| Agent | Short-Term (Session) | Long-Term (Supabase) |
|-------|---------------------|---------------------|
| Inventory | Current batch analysis state, vehicles being evaluated | Pricing patterns, seasonal trends, competitor positioning history |
| Leads | Current lead being scored, recent interactions loaded | Source quality patterns, scoring calibration data, rep-lead matching history |
| Engagement | Customer context for current draft, conversation thread | Communication templates that worked, optimal timing patterns per customer segment |
| Deals | Current analysis dataset, comparison baselines | Win/loss patterns, rep performance trends, market cycle correlations |

## 7. SUPABASE EDGE FUNCTIONS (API LAYER)

Each tool declaration maps to a Supabase Edge Function or direct client call.

```typescript
// supabase/functions/agent-tools/index.ts
import { serve } from "https://deno.land/std@0.168.0/http/server.ts";
import { createClient } from "https://esm.sh/@supabase/supabase-js@2";

serve(async (req) => {
  const { tool_name, params } = await req.json();
  const supabase = createClient(
    Deno.env.get("SUPABASE_URL")!,
    Deno.env.get("SUPABASE_SERVICE_ROLE_KEY")!
  );

  switch (tool_name) {
    case "query_supabase": {
      let query = supabase.from(params.table).select(params.select || "*");
      if (params.filters) {
        for (const [key, value] of Object.entries(params.filters)) {
          if (key.endsWith("_gt")) query = query.gt(key.replace("_gt", ""), value);
          else if (key.endsWith("_lt")) query = query.lt(key.replace("_lt", ""), value);
          else query = query.eq(key, value);
        }
      }
      if (params.order_by) {
        const [col, dir] = params.order_by.split(".");
        query = query.order(col, { ascending: dir === "asc" });
      }
      if (params.limit) query = query.limit(params.limit);
      const { data, error } = await query;
      return new Response(JSON.stringify({ data, error }));
    }

    case "store_memory": {
      const { data, error } = await supabase.from("agent_memories").insert({
        agent_name: params.metadata?.agent_name || "unknown",
        memory_type: params.memory_type,
        content: params.content,
        metadata: params.metadata || {},
        expires_at: params.ttl_days
          ? new Date(Date.now() + params.ttl_days * 86400000).toISOString()
          : null,
      });
      return new Response(JSON.stringify({ data, error }));
    }

    case "recall_memory": {
      let query = supabase
        .from("agent_memories")
        .select("*")
        .eq("is_active", true)
        .ilike("content", `%${params.query}%`)
        .order("created_at", { ascending: false })
        .limit(params.limit || 10);
      if (params.memory_type) query = query.eq("memory_type", params.memory_type);
      if (params.agent_name) query = query.eq("agent_name", params.agent_name);
      const { data, error } = await query;
      return new Response(JSON.stringify({ data, error }));
    }

    // Add cases for all other tools...
    default:
      return new Response(JSON.stringify({ error: "Unknown tool" }), { status: 400 });
  }
});
```
